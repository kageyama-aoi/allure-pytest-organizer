# 仕組み解説：なぜこの構成にしたか

このリポジトリで使っている仕組みと、それぞれを選んだ理由をまとめます。

## 全体の流れ

```
コードを main に push
   ↓
GitHub Actions が自動で起動（.github/workflows/allure-pages.yml）
   ↓
① pytest でテストを実行            → allure-results/ に結果ファイル（JSON）ができる
   ↓
② Allure 3 が結果ファイルを HTML に変換 → allure-report/ ができる
   ↓
③ GitHub Pages に公開              → https://kageyama-aoi.github.io/allure-pytest-organizer/
```

「テストを動かす人」と「結果を見る人」を分けるのが狙いです。
テスト結果を、コマンドを打たなくてもブラウザで見られる状態にします。

## 使っている部品と、選んだ理由

| 部品 | 役割 | 選んだ理由 |
|---|---|---|
| **pytest** | テストを実行する | Python の標準的なテストツール。関数を書くだけでテストになる |
| **allure-pytest** | pytest の結果を Allure 用のファイルで出力する | pytest に足すだけで動く。`@allure.title` などの日本語ラベルも使える |
| **Allure 3（CLI）** | 結果ファイルを HTML レポートに変換する | Node.js で動くため Java が不要。ローカル PC でも CI でも `npx` だけで動く |
| **allurerc.mjs** | レポートの表示設定 | 一覧を日本語の分類で並べるため（下記） |
| **GitHub Actions** | push のたびに①〜③を自動実行する | 手作業のコマンド実行をなくし、いつも最新の結果を公開できる |
| **GitHub Pages** | HTML レポートをWebページとして公開する | 無料で、URL を共有するだけで誰でも見られる |

## テストの書き方で工夫したこと

### 実ファイルを触らない（`tmp_path` と `monkeypatch`）

整理ツールはファイルを実際に移動するので、普通に動かすと自分のフォルダが散らかります。
そこで次の2つを使っています。

- `tmp_path`: pytest が用意する使い捨ての一時フォルダ。テスト後に自動で消える。
- `monkeypatch`: ツールが読む設定（整理対象のフォルダ）を、その一時フォルダに差し替える。

元のコード（`organize_files.py`）は1文字も変えていません。

### 読みやすさのための Allure の書き方

| 書き方 | 効果 |
|---|---|
| `@allure.title("...")` | レポートに日本語のテスト名を出す |
| docstring（`"""..."""`） | テストの説明文としてレポートに出る |
| `with allure.step("準備: ...")` | 「準備 → 実行 → 確認」の3ステップが見える |
| `@allure.epic / feature / story` | 一覧を分類ごとにまとめる材料になる |

### 既知のバグは `xfail(strict=True)` で記録する

対象フォルダが存在しないと、想定外のエラーで落ちるバグが見つかりました。

- 元コードは直さず、「今はこう落ちる」ことをテストに残しています。
- `xfail`: 失敗するのを承知の上で記録するマーク。レポートでは skipped と表示される。
- `strict=True`: バグが直って成功したら、逆にテストを失敗させる。「xfail を外す時期」の合図になる。

## レポートの一覧を日本語の分類にした理由

Allure 3 の標準では、一覧が「ファイル名 → クラス名」（`TestSortByExtension` など）で並びます。
これでは何のテストか分からないため、`allurerc.mjs` で並び順を変えています。

```js
groupBy: ["epic", "feature", "story"],
```

これでテストコードの `@allure.epic / feature / story` に書いた日本語が、そのまま一覧の階層になります。

補足: `defineConfig` を `import` する書き方は、`npx` で実行すると解決できず失敗したため、
普通のオブジェクトを `export default` する形にしています。

## GitHub Actions の中身

`.github/workflows/allure-pages.yml` は 2 つのジョブでできています。

| ジョブ | やること |
|---|---|
| `build` | Python と Node を用意 → pytest 実行 → Allure でレポート生成 → Pages 用に成果物を保存 |
| `deploy` | 保存した成果物を GitHub Pages に公開する（`needs: build` で build の後に実行） |

ポイント:

- **`permissions`**: `contents: read` / `pages: write` / `id-token: write` の3つが Pages 公開に必要。
- **`continue-on-error: true`（pytest の手順）**: テストが失敗してもレポートは公開する。失敗の原因を見るのがレポートの目的だから。
- **`workflow_dispatch`**: Actions 画面から手動でも再実行できる。
- **Pages の設定**: リポジトリの Settings → Pages で、Source を「GitHub Actions」にしておく必要がある。

## なぜ公開リポジトリにしたか

- GitHub Pages は、無料プランでは**公開リポジトリでしか使えない**。
- 公開した Pages は、リポジトリが非公開でもインターネット上で誰でも見られる。
- 個人の作業ファイルが入った非公開リポジトリを公開したくないため、サンプルだけを入れた**専用の公開リポジトリ**に分けた。

## まだやっていないこと

- **履歴・トレンド表示**: 実行のたびに前回の結果を引き継ぐ仕組み（Allure の history）が必要。今は毎回、その時点の結果だけを公開している。
- **`pytest-html` など他ツールとの比較**: 今回は Allure の練習が目的のため未実施。
